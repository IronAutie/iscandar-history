\subsection{Axiom V: The Coordinate-Address Identity}

The architecture used here rejects the traditional separation of logical address space and physical memory geometry, by establishing a \textbf{Bijective Identity} between a machine-word pointer $P$ (wrapped pointer, see section 5) and its corresponding lattice coordinate $\vec{C}$.\\ 

In a system of depth $k$ and arity $A$, any specific sector is represented by a coordinate vector:
\begin{equation}
    \vec{C} = (i_1, i_2, \dots, i_k) \quad \text{where} \quad 0 \leq i_n < A
\end{equation}

The address $P$ is not an arbitrary token, but the scalar projection of this vector into the linear address space. The isomorphism is defined by the construction:
\begin{equation}
    P = \sum_{n=1}^{k} i_n \cdot A^{k-n}
\end{equation}

For the demonstration project of this paper, ($A=32, k=3$), the address of a sector located at $(\text{Plane } p, \text{Row } r, \text{Sector } s)$ is clearly enumerable from the geometry:
\begin{equation}
    P = (p \cdot 32^2) + (r \cdot 32^1) + (s \cdot 32^0)
\end{equation}

\subsection{Symmetric Coalescence Mechanics}
To maintain determinism our deallocation process mirrors the efficiency of the allocation logic, a state update performed upon the occupancy counters. The bit-address of any Sector ($S_0$) is a fixed function of its coordinates. Updating the occupancy counters ($\Gamma$) thus consumes a predictable instruction count ($\iota_{base}$) identical to the initial resolution.

\begin{enumerate}

Because the lattice depth is fixed at $n = 3$, the time complexity for deallocation is defined by the same path-specific constraints as allocation.

\section{Observations}

Earlier sections established \textbf{Iscandar} as deterministic within the primary scope of this paper. However, it exhibits properties warranting distinct architectural observations.

\subsection{As an Extension to Binary Buddy Systems}
The binary buddy system, pioneered by Knowlton [12] and Knuth [13], sought to minimize search latency through a power-of-two partitioning scheme ($R=2$). While this approach facilitates efficient coalescence, its search complexity remains fundamentally constrained to $O(\log_{2} n)$. As modern memory address spaces scale alongside processor word sizes, the increasing logarithmic depth of these trees drives significant latency. Furthermore, at high utilization, binary buddy systems trigger ``stalling'' behaviors; the search algorithm must traverse increasingly fragmented leaf nodes, which inevitably erodes deterministic performance.\\

We generalize buddy system principles to an \textbf{Arbitrary Radix} ($R=\mathcal{A}$). By shifting from a binary tree to a high-radix fractal lattice, we collapse the depth of the search space to a fixed architectural constant $n$. This structural shift moves memory management from the domain of probabilistic searching to the domain of \textbf{Geometric Coordinate Resolution}.

\subsection{As a Symmetric Voronoi Partition}
As detailed in the Architectural Axioms (Section 2.1), this lattice functions as a \textbf{Symmetric Voronoi Partition}, where the adjacency of ``buddies'' is a pre-baked geometric property of the address space rather than a calculated proximity, as shown in Section 5.2.\\ 

In this model, adjacency is defined by a partition's total volume \textbf{associating} with its handle (a wrapped pointer resolved in Section 9.4) rather than the Euclidean distance of individual points from a centroid. rather than the Euclidean distance of individual points from a centroid, as established in the geometric rules of the address space.\\

Instead, they are architecturally invariant, defined strictly by the Structural Arity ($\mathcal{A}$) and the hierarchical depth ($k$) established in the Axioms. \section{Description of Instruction Groups}

We map each instruction group to a specific predicate of the \textbf{Iscandar} hierarchy established in the Architectural Axioms. This ensures the hardware execution is a transparent reflection of the underlying mathematics. Here, we assume a 32-radix descent where each level acts as a ``Gate'' that must be cleared to reach the subsequent tier.

\subsection{Phase I: The Admissibility Gate (Level 3)}

\vspace{12pt}
\setcounter{equation}{14}
\noindent \textbf{Predicate:} 
\begin{equation}
    L \in \Gamma_{Apex} \iff \Gamma_{Apex} \leftarrow \Gamma_{Apex} + L
    \label{eq:predicate_apex}
\end{equation}
\vspace{12pt}

\begin{enumerate}
    \item \textbf{Instruction Group 1:} Load Global Registrar: Fetch the 16-bit register located at the Apex sector address as defined in the Cube Scale Allocator.
    \item \textbf{Instruction Group 2:} Admissibility Comparison: Compare against the requested magnitude $L$. If False: Immediate Exit (Fast-Fail) as required by the Global Registrar's heuristics. If True: Increment by the requested magnitude.
\end{enumerate}

\subsection{Phase II: The Plane-Level Resolution (Level 2)}

\vspace{12pt}
\setcounter{equation}{15}
\noindent \textbf{Predicate:} 
\begin{equation}
    P_{\text{Plane}} \iff \sum_{i \in \text{Plane}} (\text{Row}[\text{Inclusion}]) \ge L
    \label{eq:predicate_plane}
\end{equation}
\begin{center}
    \small\textbf{The Plane Inclusion Predicate}
\end{center}
\vspace{12pt}

\begin{enumerate}
    \setcounter{enumi}{2}
    \item \textbf{Instruction Group 3:} Index Plane Metadata: Using the address bits, index into the 32-radix plane metadata table.
    \item \textbf{Instruction Group 4:} Load Row-Summary: Fetch the 15-bit metadata for the target plane summarizing the 32 constituent rows as established in Axiom II.
    \item \textbf{Instruction Group 5:} Candidate Selection: Evaluate the plane-state to identify the first row-sequence that satisfies the weld.
    \item \textbf{Instruction Group 6:} Heuristic Branch/Scan: Evaluate the 32-radix plane metadata scan to confirm the steering vector.
\end{enumerate}

\subsection{Phase III: The Row-Level Weld (Level 1)}

\vspace{12pt}
\setcounter{equation}{16}
\begin{equation}
    \text{Weld} \iff \text{RHL}(\text{Row}_n) + \text{Intermediates} + \text{LHL}(\text{Row}_{n+m}) \ge L
    \label{eq:predicate_weld}
\end{equation}
\begin{center}
    \small\textbf{The Weld Predicate for Multi-Block Resolution}
\end{center}
\vspace{12pt}

\begin{enumerate}
    \setcounter{enumi}{6}
    \item \textbf{Instruction Group 7:} Leading Fragment Access (RHL): Perform a Look-Up Table (LUT) lookup on the starting row's tail.
    \item \textbf{Instruction Group 8:} Trailing Fragment Access (LHL): Perform a LUT lookup on the final row's head.
    \item \textbf{Instruction Group 9:} Scalar Summation: Add Lead + Intermediates + Trail, maintaining the Contiguity Guarantee.
    \item \textbf{Instruction Group 10:} Weld Validation: Compare the result against $M$ to finalize the inter-row continuity.
\end{enumerate}

\subsection{Phase IV: The Bit-Lattice Isolation (Level 0)}

\vspace{12pt}
\setcounter{equation}{17}
\noindent \textbf{Predicate:} 
\begin{equation}
    P_{\text{leaf}} \iff 
    \begin{cases} 
    \text{Oracle}_{C}(S_{\text{word}}, L) & \text{if } L \le \mathcal{A}/4 \\
    \text{Oracle}_{L}(S_{\text{word}}, L) \lor \text{Oracle}_{R}(S_{\text{word}}, L) & \text{if } L > \mathcal{A}/4
    \end{cases}
    \label{eq:predicate_leaf}
\end{equation}
\begin{center}
    \small\textbf{The Leaf-Tier Path Selection Predicate}
\end{center}
\vspace{12pt}

\begin{enumerate}
    \setcounter{enumi}{10}
    \item \textbf{Instruction Group 11: Path Selection (Nano vs. Tiny):} The logic evaluates the request magnitude $L$. If $L \le \mathcal{A}/4$, the system engages the Nano path; otherwise, the bimodal Tiny path is engaged.
    
    \item \textbf{Instruction Group 12: Bimodal Execution (Tiny Path):} For Tiny requests, the system executes a primary probe via the Left Oracle. Upon a null result, a deterministic secondary probe via the Right Oracle is triggered to capture straddle-runs.
    
    \item \textbf{Instruction Group 13: Atomic Resolution (Nano Path):} For Nano requests, the system performs a single-cycle intersection using the Center Oracle to isolate the seed polytope.

    \item \textbf{Instruction Group 14: Triangle Projection:} The successfully resolved bit-run from either path is mapped to the physical offset, finalizing the Atomic Polytope isolation.
\end{enumerate}

\section{Desk Check Summary: Nano and Tiny Resolutions ($L \le \mathcal{A}$)}

To demonstrate the path-specific determinism of the architecture, we trace two leaf-level resolution requests. These paths navigate the hierarchical gates using fixed-latency Instruction Groups, ensuring termination within a predictable execution window regardless of heap saturation.

\begin{enumerate}
    \item \textbf{Admissibility (Gate 3):} For any request $L$, the Global Registrar fetches the 16-bit register at the Apex sector address. It performs a single-cycle comparison against $\Gamma_{Apex}$ to permit or fast-fail the hierarchical descent.
    
    \item \textbf{Hierarchical Steering (Gates 2 and 1):} The system applies the Rotational Steering Vector ($\vec{R}$) to select a candidate Plane and Row. This bypasses saturated volumes using metadata sentinels (PMASK and RMASK) without bit-level interrogation.

    \item \textbf{The Nano Path ($L \le \mathcal{A}/4$):}
    \begin{itemize}
        \item \textbf{Mechanism:} This path isolates a single byte-aligned segment of the Row to extract a seed polytope.
        \item \textbf{Atomic Resolution:} The hardware indexes the \textbf{Center Oracle} for a single-pass intersection.
        \item \textbf{Geometric Event:} An \textit{Atomic Intersection} maps the Row's bit-pattern directly to an exact fit of available sectors.
    \end{itemize}

    \item \textbf{The Tiny Path ($\mathcal{A}/4 < L \le \mathcal{A}$):}
    \begin{itemize}
        \item \textbf{The First Bite:} To mitigate the fragmentation inherent in single-pass lookups, the system first indexes the \textbf{Left Oracle} to identify an eligible contiguous run.
        \item \textbf{The Second Bite:} If the primary pass returns a null state, the system immediately triggers a deterministic secondary probe via the \textbf{Right Oracle}. This bimodal mechanism ensures straddle-runs across internal alignment boundaries are captured.
    \end{itemize}
    
    \item \textbf{Lattice Commitment:} The resulting run is mapped to a pointer of a given bit offset and length. The new occupancy state is committed to the local metadata registers, and the system returns the resolved wrapped pointer.
\end{enumerate}

\noindent \textbf{Verification:} Whether the system uses an Oracle to resolve a request through a single-cycle Nano intersection or a dual-pass Tiny probe, the execution path length is fixed. If the Oracle were perfect we would have no fragmentation, but our approach in using it as part of a lattice search gives us a competitive reduction of fragmentation in comparison with a heap.

\subsection{Center Oracle}
   
\begin{Iscandar}[OracleCenter.ps1]
# Manufactures the 38.6GB Center Oracle Blob
# Layout: 2^32 rows x 9 columns (k=0..8)
# Logic: Motorola Big-Endian (Bit 0 = MSB/Left). First-fit from Left.

$FilePath = "OracleCenter.bin"
$Stream = [System.IO.File]::Create($FilePath)
$Writer = New-Object System.IO.BinaryWriter($Stream)

Write-Host "Manufacturing Center Oracle..."

# Iterate through all 2^32 possible occupancy states
for ([double]$S_double = 0; $S_double -lt 4294967296; $S_double++) {
    $S = [uint32]$S_double

    # Columns k=0 to 8 represent the requested allocation length
    for ($k = 0; $k -le 8; $k++) {
        if ($k -eq 0) {
            $Writer.Write([byte]0) # Redundant column for k=0
            continue
        }

        $foundPos = 0xFF #  indicates no block of length k exists

        # Motorola Big-Endian Scan from (Bit 0) to (Bit 31)
        # Stop at first success to ensure "Closest to Left" packing.
        for ($pos = 0; $pos -le (32 - $k); $pos++) {
            
            # Construct Motorola mask: k bits starting at 'pos'
            # Calculation: (2^k - 1) shifted to
            # correct Motorola bit position
            $baseMask = [uint32]([math]::Pow(2, $k) - 1)
            $mask = $baseMask -shl (32 - $k - $pos)
            
            # Deterministic Bit-Check
            if (($S -band $mask) -eq 0) {
                $foundPos = [byte]$pos
                break # TERMINATE: Found the leftmost sequence
            }
        }
        $Writer.Write($foundPos)
    }

    # Status heartbeat for the factory floor
    if ($S_double % 100000000 -eq 0) { 
        $progress = [math]::Round(($S_double/4294967296)*100, 2)
        Write-Host "Progress: $progress% ($S_double rows processed)" 
    }
}

$Writer.Close()
$Stream.Close()
Write-Host "Iscandar Center Oracle Manufacture: Complete."
\end{Iscandar}

\begin{Iscandar}[OracleLeft.ps1]

# Logic: Trailing Run (Ends at LSB)
$P = "OracleLeft.bin"
$S_i = [System.IO.File]::Create($P)
$W = [System.IO.BinaryWriter]::new($S_i)

for ([double]$d=0; $d -lt 4gb; $d++) {
  $S = [uint32]$d

  # Check LSB (Motorola Bit 31)
  if (($S -band 1) -ne 0) {
    $A = [byte]255 # Blocked Case
    $B = [byte]0
  } else {
    $r = 0 # Length counter
    for ($i=0; $i -lt 32; $i++) {
      $m = [uint32]1 -shl $i
      if (($S -band $m) -eq 0) {
        $r++
      } else { break }
    }
    $A = [byte]$r # Byte A: Length
    # B: Start Pos (Relative to MSB)
    $B = [byte](32 - $r) 
  }
  $W.Write($A); $W.Write($B)

  if ($d % 100mb -eq 0) {
    $p = [math]::Round(($d/4gb)*100,2)
    Write-Host "Progress: $p %"
  }
}
