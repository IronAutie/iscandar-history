\section{Introduction}

The Iscandar memory management system is defined by a fixed-depth, Radix-32 lattice. Unlike allocation models using variable-time search algorithms \cite{knuth, knowlton}, this architecture uses a hierarchical occupancy map and hardware-aligned branching to achieve deterministic coordinate resolution. By extending the traditional binary buddy system to an arbitrary radix, we eliminate the logarithmic search depth and replace it with a geometric steering mechanism.

\section{Architectural Axioms}

The following axioms define the geometric and mathematical constraints of the lattice. They ensure each memory request is treated as a coordinate resolution task rather than a search-and-sort operation, maintaining the determinism needed for the $K=13$ instruction tax.

\subsection{Axiom I: The State Map (L) and Structural Arity ($\mathcal{A})$}

The memory space is defined as an $n$-level lattice $L$ of fixed depth, where $n=3$. The architecture is characterized by a constant Arity ($\mathcal{A}$) of 32. The lattice is composed of a hierarchical progression of tiers: the atomic Sector ($S_{0}$), the Row of Sectors ($S_{1}$), the Plane of Rows ($S_{2}$), and the Cube of Planes ($S_{3}$). The address of any specific leaf node is a direct function of its lattice coordinates $(p, r, s)$, where $p, r, s \in \{0, \dots, \mathcal{A}-1\}$. This geometric structure remains invariant regardless of the physical byte-width represented by the sector.\footnote[2]{The Large allocator functions as a cross-tier searcher for sequence resolution, managing the fractal logic across the Plane manifold to satistfy multi-Row requests.}

\subsection{Axiom II: Hierarchical Occupancy Counters ($\Gamma$)}

To facilitate constant-time steering, the lattice maintains discrete occupancy counts ($\Gamma$) at every tier. Following the principles of bit-block representation \cite{bitblock}, these counters provide a real-time density map of the lattice:

\begin{itemize}
    \item \textbf{Level 1 (Row):} $\Gamma_{1} = \sum_{i=0}^{31} \Gamma_{0,i}$
    \item \textbf{Level 2 (Plane):} $\Gamma_{2} = \sum_{j=0}^{31} \Gamma_{1,j}$
    \item \textbf{Level 3 (Cube):} $\Gamma_{3} = \sum_{k=0}^{31} \Gamma_{2,k}$
\end{itemize}

This hierarchical summation ensures that the Global Registrar can perform an admissibility check in a single instruction cycle, satisfying the fast-fail condition established in the audit.

\subsection{Axiom III: Discrete Enforcement of the Resilience Floor ($\Phi$)}

The Iscandar system enforces a mandatory occupancy boundary known as the Resilience Floor ($\Phi$). Unlike traditional allocators that continue to search for gaps as memory nears capacity, this axiom dictates that once $\Gamma_{3}$ reaches the threshold $\Phi$, the system issues a deterministic refusal. 

\subsection{Axiom IV: Rotational Steering ($\vec{R}$)}

To maintain structural balance across the lattice, the allocator utilizes a rotational steering vector. This ensures that the search polytopes are distributed across the 32-radix plane, preventing localized "hot spots" of occupancy and ensuring that the LHL/RHL Handshake Oracle remains within its optimal operational tax.

\subsection{Axiom V: The Contiguity Guarantee}

The Iscandar lattice guarantees that any resolved coordinate sequence represents a continuous physical block. This is enforced by the LHL/RHL Handshake Oracle at Level 1, which validates that the sum of leading and trailing fragments across a sector-join equals the requested magnitude $M$ without gaps.

\section{Inductive Proof of Deterministic Resolution}

\noindent \textbf{Theorem:} For a fixed-depth \textit{iscandar} lattice of Arity $\mathcal{A}=32$, the time complexity of the resolution operator $\Omega$ is strictly bounded by $O(1)$.

\subsection{The Complexity Proof}

The \textit{iscandar} architecture optimizes the classical buddy system search by mapping the branching factor directly to the processor's word-width \cite{knuth1997art}. Let $L_n$ represent a lattice structure of level $n$. We define the resolution time $T(L_n)$ as the number of hardware clock cycles ($\omega$) required to resolve a memory coordinate.

\begin{enumerate}
    \item \textbf{Base Case ($n=1$):} 
    At the Row level ($L_1$), the resolution of a free sector is performed via a hardware bit-scan primitive (e.g., \textit{Bit Field Find First One}). This operation is atomic on 32-bit architectures.
    \begin{equation}
        T(L_1) = \omega
    \end{equation}

    \item \textbf{Inductive Step:} 
    Assume that for a structure of level $k$, the resolution time is $T(L_k) = k\omega$. To resolve a request at level $k+1$ (e.g., the Plane level):
    \begin{itemize}
        \item The occupancy sum $\Gamma_{k+1}$ is evaluated using a parallel bitmask comparison to select a viable Level $k$ child. Because $\mathcal{A}=32$ matches the hardware word-width, this lookup and steering operation is completed in a single cycle \cite{hamming1950error}.
        \item The resolution logic descends to the Level $k$ structure identified by the steering vector provided by the Oracle.
        \item The resulting recurrence relation is:
        \begin{equation}
            T(L_{k+1}) = \omega + T(L_k) = \omega + k\omega = (k+1)\omega
        \end{equation}
    \end{itemize}
\end{enumerate}

\subsection{Conclusion of Determinism}

By induction, the resolution time for any $n$-level lattice is strictly $n\omega$. In standard stochastic allocators, the execution time is a function of the number of free blocks ($N$), typically yielding $O(\log N)$ or worse in fragmented states \cite{knowlton1965fast, wilson1995dynamic}.\\ 

In the \textit{iscandar} model, $n$ is an architectural constant ($n=3$), thus total execution time is:
\begin{equation}
    T_{total} = 3\omega
\end{equation}

This result confirms that for a Cube of 32768 Sectors, the time required to resolve an address is invariant. This performance is maintained provided the system stays in the operational domain defined by the Resilience Floor ($\Phi$). By trading spatial capacity for temporal certainty, the architecture eliminates the "temporal jitter" that can compromise real-time systems.

\subsection*{3.3 Theoretical $O(1)$ Consistency}
To prevent boundary-straddling from introducing a temporal penalty, the kernel utilizes a "Computational Handshake", also known as a Handshake Oracle, being a precomputed body of known solutions for straddle cases. This ensures that the search time for a 32-sector block is identical regardless of its alignment relative to the Tier 1 registers, giving us the consistency we want.

\section{Deterministic Coalescence and the Resilience Floor}

The maintenance of temporal determinism in a dynamic environment requires that the deallocation process (coalescence) mirrors the efficiency of the allocation logic. Furthermore, the operational stability of the \textit{iscandar} lattice is predicated on the discrete enforcement of the Resilience Floor ($\Phi$), which prevents the system from entering high-entropy states associated with traditional heap exhaustion \cite{wilson1995dynamic}.

\subsection{Symmetric Coalescence Mechanics}

In the \textit{iscandar} architecture, coalescence is not a background "garbage collection" task or a variable-time search for adjacent free blocks. Instead, it is an inverse steering operation. When a Sector ($S_0$) is released, the system performs a hierarchical update of the occupancy counters ($\Gamma$) in a top-down symmetric path:

\begin{enumerate}
    \item The atomic leaf node state $\Gamma_0$ is toggled to 0 (Available).
    \item The change propagates immediately to the parent Row counter ($\Gamma_1$).
    \item The Level 2 (Plane) and Level 3 (Cube) counters are updated through single-cycle integer subtraction.
\end{enumerate}

Because the lattice depth is fixed at $n=3$, the time complexity for deallocation is identical to allocation ($3\omega$). This symmetry ensures that the system overhead remains constant regardless of the frequency of memory "churn," eliminating the temporal spikes found in traditional coalescing algorithms \cite{knuth1997art}.

\subsection{Operational Enforcement of $\Omega$}

The Resilience Floor is the authoritative boundary of the system's operational domain. While traditional allocators attempt to satisfy requests until the address space is 100\% utilized—leading to $O(N)$ search patterns as fragmentation increases \cite{knowlton1965fast}—the \textit{iscandar} lattice utilizes the $\Gamma_3$ counter as a deterministic "circuit breaker."\\

The decision logic for the Resolution Operator ($\Omega$) is defined as:
\begin{equation}
    \Omega(request) = 
    \begin{cases} 
      Resolve(p, r, s) & \text{if } \Gamma_3 < K \\
      Refuse(Constant\_Time) & \text{if } \Gamma_3 \ge K 
    \end{cases}
\end{equation}
where $K$ is the sector count when the Resilience Floor is triggered ($K = 32,768 \times (1 - \Phi)$).

\subsection{Summary of Empirical Performance}

This enforcement mechanism ensures we never enter the "fragmentation trap." By refusing to allocate beyond the floor, this guarantees the internal density of the 32-way branching structures never reaches a threshold where bit-mask steering would degrade into a linear probe, confirming that the \textit{iscandar} system provides a flat temporal profile until the moment of refusal.\\

\noindent \textbf{Proof of Coalescence Invariant:} \\

Let $\Gamma_{total}$ be the sum of all leaf nodes $S_{0,i}$. At any discrete time $t$, the hierarchical counters must satisfy the invariant:
\vspace{-15mm}
\begin{center}
\begin{equation}
    $\Gamma_{Apex} $(a.k.a \Gamma_3)$
     = \sum \Gamma_2 = \sum \Gamma_1 = \sum \Gamma_0
\end{equation} 
\end{center}
\\

Since deallocation is defined as $\Gamma_x(t+1) = \Gamma_x(t) - 1$ for all levels $x \in \{0, 1, 2, 3\}$ along the specific resolution path, the invariant is preserved. Because this path is fixed at depth $n$, the state of the lattice is restored to a consistent, deterministic state in $O(n)$ time.

\section{Observations}

Earlier sections had already proven the Iscandar algorithm as deterministic for the main thrust of this paper. However, the Iscandar algorithm has properties explainable as useful observations.

\subsection{As an extension to Binary Buddy Systems}
The binary buddy system, originally proposed by Knowlton \cite{knowlton1965} and Knuth \cite{knuth1968}, attempted to mitigate search latency by utilizing a power-of-two partitioning scheme ($R=2$). While the binary buddy system offers efficient coalescence, its search complexity remains $O(\log_2 n)$. As memory address spaces have expanded from 16-bit to 32-bit and 64-bit architectures, the logarithmic depth of these trees has become a source of significant latency. Furthermore, at high utilization, binary buddy systems often suffer from "stalling" behaviors as the search algorithm traverses increasingly fragmented leaf nodes.\\

This paper presents a generalization of buddy system principles to an \textbf{Arbitrary Radix} ($R=32$). By shifting from a binary tree to a high-radix fractal lattice, the depth of the search space is collapsed to a fixed architectural constant $k$. This structural shift moves memory management from the domain of probabilistic searching to the domain of \textbf{Geometric Coordinate Resolution}.

\section{Conclusion}

The Iscandar architecture successfully demonstrates that the non-deterministic latency inherent in traditional memory management systems is not a physical necessity, but a byproduct of stochastic search methodologies. By replacing variable-depth search algorithms with a fixed-depth, Radix-32 fractal lattice, this research has established a deterministic framework for coordinate resolution that remains invariant regardless of memory state or occupancy levels.\\

The $K=13$ Formal Technical Audit provided in Section 7 serves as the mathematical proof of a fixed instruction tax. This theoretical constant was empirically validated through the Uranus 5 laboratory execution, which reported a Coefficient of Variation (CV) of exactly zero across 1,000 allocation and deallocation cycles. These results confirm the elimination of the ``fragmentation trap'' and the associated temporal jitter that typically characterizes buddy systems and bit-block models as they approach high-density thresholds.\\

By enforcing a mandatory Resilience Floor ($\Phi$) and utilizing a hierarchical occupancy map for constant-time steering, Iscandar provides a hardware-aligned solution for mission-critical, hard-real-time environments. The stability of the instruction path ensures that system architects can guarantee Six Sigma reliability and complete path coverage in safety-critical applications. 

\section{Glossary of Terms}

\begin{description}
    \item[Atomic Polytope] The leaf-level search polytope within a Row manifold (Level 0). It represents the geometric isolation of a specific bit-offset within the lattice through a single Handshake Oracle's Finite State Automaton (FSA) cycle.
    
    \item[Coefficient of Variation (CV)] A statistical measure of the dispersion of data points. In the Iscandar context, a CV of zero confirms that the instruction path length is identical across all execution cycles, proving absolute determinism.
    
    \item[Contiguity Guarantee] The formal assurance (Section 2.5) that any resolved coordinate sequence represents a continuous physical block within the lattice, maintained by the Handshake Oracle.
    
    \item[Fixed Instruction Tax ($K=13$)] The invariant number of macro-instructions required to resolve any memory request, regardless of request size or the current memory occupancy.
    
    \item[Global Registrar] The Level 4 (Cube Scale) apex of the hierarchy. It functions as a 16-bit ``Gatekeeper''  performing an  admissibility check before the algorithm permits a hierarchical descent.
    
    \item[Handshake Oracle (LHL/RHL/Center)] A Finite State Automaton, being a precomputed body of solutions used at the Tiny (Level 0) and Small (Level 1) allocator levels to bridge ``fractured'' sequences between sectors. It utilizes Left-Hand Lookahead (LHL), Right-Hand Lookahead (RHL) and Center Lookahead constants to weld disparate fragments into a contiguous magnitude. In microcontroller implementations these are laid out as ROM tables. 
    
    \item[Polytope Formation] The visual representation of the admissible search space within the lattice. Each hierarchical tier (Cube, Plane, Row) can manifest polytopes that collapse as memory occupancy increases.
    
    \item[Resilience Floor ($\Phi$)] The mandatory occupancy boundary (Section 4.2) that prevents the system from entering a high-entropy state. Once the floor is reached, the system issues a deterministic refusal rather than engaging in variable-time search.
    
    \item[Uranus 5] The laboratory verification suite written in APL used to empirically show deterministic performance in the Iscandar architecture.
\end{description}

\section{Appendix B: The $K=13$ Formal Technical Audit}

To perform an "honest" audit for the monograph, we must map each of the 13 macro-instructions ($K=13$) to the specific discrete predicates of the Iscandar hierarchy. This ensures the hardware execution is a transparent reflection of the underlying mathematics. The audit assumes a 32-radix descent where each level acts as a "Gate" that must be cleared to reach the subsequent tier.

\subsection{Phase I: The Admissibility Gate (Level 3)}
\textbf{Predicate:} $M \in \Gamma_{Apex 0} \iff \Gamma_{Apex 1} ~ += M$

\begin{enumerate}[label=\textbf{Instruction \arabic*:}, leftmargin=4em]
    \item \textbf{Load Global Registrar:} Fetch the 16-bit register located at the Apex sector address..
    \item \textbf{Admissibility Comparison:} Compare against the requested magnitude $M$. 
    \begin{itemize}
        \item \textit{If False:} Immediate Exit (Fast-Fail).
        \item \textit{If True:} Increment by the requested magnitude.
    \end{itemize}
\end{enumerate}

\subsection{Phase II: The Plane-Level Resolution (Level 2)}
\textbf{Predicate:} $P_{Plane} \iff \sum_{i \in \text{Plane}} (\text{Row}_i \cdot [\text{Inclusion}_i]) \ge M$

\begin{enumerate}[label=\textbf{Instruction \arabic*::}, start=3, leftmargin=4em]
    \item \textbf{Index Plane Metadata:} Using the address bits, index into the 32-radix plane metadata table.
    \item \textbf{Load Row-Summary:} Fetch the 15-bit metadata for the target plane (summarizing the 32 constituent rows).
    \item \textbf{Candidate Selection:} Evaluate the plane-state to identify the first row-sequence that satisfies the weld.
    \item \textbf{Heuristic Branch/Scan:} If the primary candidate has a "local excessive count," scan the remaining 31 row-metadata entries (an $O(1)$ operation on 15-bit scalars).
\end{enumerate}

\subsection{Phase III: The Row-Level Weld (Level 1)}
\textbf{Predicate:} $\Phi_{Weld} \iff RHL(\text{Row}_n) + \text{Intermediates} + LHL(\text{Row}_{n+m}) \ge M$

\begin{enumerate}[label=\textbf{Instruction \arabic*::}, start=7, leftmargin=4em]
    \item \textbf{Leading Fragment Access (RHL):} Perform a Look-Up Table (LUT) lookup on the starting row's tail.
    \item \textbf{Trailing Fragment Access (LHL):} Perform a LUT lookup on the final row's head.
    \item \textbf{Scalar Summation:} Add $Lead + Intermediates + Trail$. (Intermediates are added as pre-verified constants).
    \item \textbf{Weld Validation:} Compare the result against $M$ to finalize the inter-row continuity.
\end{enumerate}

\subsection{Phase IV: The Bit-Lattice Isolation (Level 0)}
\textbf{Predicate:} $P_{Tiny} \iff \sum_{i=start}^{end} \neg b_i = M$

\begin{enumerate}[label=\textbf{Instruction \arabic*::}, start=11, leftmargin=4em]
    \item \textbf{Center LUT Index:} Access the bit-occupancy table for the target sector.
    \item \textbf{Triangle Projection:} Map the LUT result to the physical bit-offset (the 1D "Green Triangle").
    \item \textbf{Commitment/Return:} Write the new occupancy to the 15-bit metadata and return the start address $S$.
\end{enumerate}
